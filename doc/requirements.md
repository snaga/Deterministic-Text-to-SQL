# 要件定義 (requirements.md)

## 概要
本システムは、TypeSafe AIの超高速判別モデル「Jev」と型安全なSQL抽象構文木（AST）ビルダーを連携させ、自然言語の質問から高信頼・決定論的なSQLをミリ秒オーダーで自動合成するText-to-SQLエンジンです。LLMに直接SQL文字列を記述させず、セマンティクス（主テーブル、集約軸、指標、フィルタ）のスロット抽出と外部キーグラフ探索、型安全ASTコンパイルを分離することで、ハルシネーションと構文エラーを物理的に遮断します。

## 前提条件
- データベースのテーブル定義、カラム定義、および外部キー（FK）関係がセマンティックメタデータとして事前に提供されていること。
- TypeSafe Jev API（または互換エンドポイント）が利用可能であり、ミリ秒オーダーでレスポンスが返却されること。
- 実行環境にPython 3.11以上が導入されていること。

## 制約条件
- 対象とするSQLはデータ参照クエリ（`SELECT` 文）に限定し、データの破壊・変更（`INSERT`, `UPDATE`, `DELETE`, `DROP`）を行うクエリは一切生成してはならない。
- 自然言語解析からSQL生成完了までのトータル処理時間は、ネットワーク遅延を含め通常 100ms 未満を目標とし、内部処理（グラフ探索＋ASTコンパイル）は 10ms 未満で完了しなければならない。
- SQLインジェクション攻撃や存在しないカラムの参照を防ぐため、固定区分値はメタデータのホワイトリスト定義にバインドされなければならない。

## 要件

### 要件カテゴリA: セマンティックメタデータ管理 (Schema & Metadata)

- 要件 A-1: Apache Ossie 標準セマンティックメタデータのロードと検証
  - ユーザーストーリー:
    - 私はデータエンジニアとして、業界標準の Apache Ossie 形式（YAML または JSON）でデータセット、リレーション、およびメトリクスを定義したい。なぜなら特定のベンダーや実装に依存せず、セマンティックモデルを再利用可能にするためだ。
  - 受け入れ基準:
    - [State-driven] Apache Ossie 形式のメタデータ定義ファイル（YAML または JSON）がロードされたとき、システムは `datasets`、`fields`、`relationships`、`metrics`、および `custom_extensions` をパース・バリデーションし、内部スキーマモデルに保持しなければならない。
    - [Unwanted-behavior] 仕様に適合しない不正な Ossie ファイルや必須項目（`datasets` 等）が欠如している場合、システムは明確なバリデーションエラーを出力して処理を中断しなければならない。

- 要件 A-2: 外部キー関係のグラフ構造化
  - ユーザーストーリー:
    - 私はシステムアーキテクトとして、Ossie 内の `relationships` 定義から外部キー結合関係をグラフデータ構造として保持させたい。なぜなら複数テーブル間のJOIN結合経路を自動かつ決定論的に特定するためだ。
  - 受け入れ基準:
    - [Event-driven] スキーマメタデータが正常に読み込まれたとき、システムはテーブルをノード、`from_columns` と `to_columns` による結合参照を無向エッジとするスキーマグラフ（NetworkX）を自動構築しなければならない。

- 要件 A-3: メトリクス定義および自然言語シノニムの保持
  - ユーザーストーリー:
    - 私はアナリストとして、KPI や集計指標の計算式および自然言語の同義語（シノニム）をメタデータで一元管理したい。なぜなら表記揺れを正しく解釈し、常に一貫したビジネス計算式で SQL を合成するためだ。
  - 受け入れ基準:
    - [State-driven] メタデータに `metrics`（集約計算式）および `ai_context.synonyms`（類義語）が定義されているとき、システムは各指標の計算表現（ANSI_SQL）と自然言語エイリアスを保持し、クエリ解釈および AST 合成時に照合可能としなければならない。

- 要件 A-4: 階層オントロジー定義の外部ロード
  - ユーザーストーリー:
    - 私は業務設計者として、地域と国、大カテゴリと小カテゴリなどの親子関係や包含値マッピングを設定ファイルから読み込ませたい。なぜならコードを変更せずにオントロジー縮退ルールをカスタマイズするためだ。
  - 受け入れ基準:
    - [State-driven] メタデータの `custom_extensions` に階層オントロジー（`hierarchies`）が指定されているとき、システムは親子関係および包含値マッピングを読み込み、オントロジー縮退器に供給しなければならない。

### 要件カテゴリB: 超並列スロット抽出 & Jev連携 (Slot Extraction)

- 要件 B-1: メタデータ駆動のマルチスロット並列抽出
  - ユーザーストーリー:
    - 私は分析ユーザーとして、任意のデータベース定義に対して自然言語で質問した際、対象テーブル・集計軸・指標・抽出条件を正しく解釈してほしい。なぜならスキーマごとにコードを個別改修する手間をなくすためだ。
  - 受け入れ基準:
    - [Event-driven] ユーザーが自然言語クエリを入力したとき、システムはロードされた Ossie メタデータ（テーブル一覧、ディメンション一覧、メトリクス一覧）から Jev 判別用 Criteria を動的に構成し、TypeSafe Jev API を呼び出して主テーブル、集約ディメンション、指標カラム、およびフィルタスロットを同時に抽出・解析しなければならない。
    - [Ubiquitous] システムは、Jev APIの推論ステート構築時にスキーマメタデータの定義情報を適切にコンテキストとして渡さなければならない。

- 要件 B-2: 自然言語シノニムに基づくホワイトリスト Choice バインド
  - ユーザーストーリー:
    - 私はセキュリティ担当者として、固定区分値やコード値が自然言語の揺れから正しく安全な値へ正規化されることを求めたい。なぜならSQLインジェクションや表記揺れによる検索ミスを防ぐためだ。
  - 受け入れ基準:
    - [Event-driven] メタデータに `ai_context.synonyms` または許容値リスト（values）が定義されているカラムについて、ユーザーの入力から値が抽出されたとき、システムは定義済みホワイトリストのChoice値に厳格にバインドしなければならない。
    - [Unwanted-behavior] 定義外の不正な文字列やSQLインジェクションを試みる入力が与えられた場合、システムは無効な値として除外し、不正なWHERE句を生成してはならない。

### 要件カテゴリC: 決定論的JOIN解決 & AST生成 (Graph & Compiler)

- 要件 C-1: 最短経路による外部キー自動結合
  - ユーザーストーリー:
    - 私はクエリ作成者として、離れたテーブル間の集計であっても自動的に正しいJOIN句を組み立ててほしい。なぜなら中間テーブルを手動で指定する煩雑さを解消するためだ。
  - 受け入れ基準:
    - [Event-driven] 複数のテーブルに跨るスロット（例: ディメンションと指標が別テーブル）が指定されたとき、システムはスキーマグラフ上の最短経路アルゴリズムを実行し、過不足のない中間テーブルと結合条件（ON句）を決定論的に導出しなければならない。

- 要件 C-2: 階層オントロジーによる冗長条件の縮退
  - ユーザーストーリー:
    - 私は業務アナリストとして、「アジアの日本」のように包含関係のある条件を指定した際、無駄な二重フィルタを除去してほしい。なぜならクエリの実行効率と可読性を保つためだ。
  - 受け入れ基準:
    - [State-driven] 親子階層関係（例: 地域と国）にある複数のフィルタが同時に指定されたとき、システムはオントロジーグラフに基づいて冗長な親条件を自動的に縮退（Deduplication）し、子条件のみをWHERE句に反映しなければならない。

- 要件 C-3: 複数SQLダイアレクトへの型安全ASTトランスパイル
  - ユーザーストーリー:
    - 私はマルチクラウドおよびローカル環境の開発者として、生成されたSQLをPostgreSQL、DuckDB、SQLite、Snowflake、BigQueryなどの指定データベースでエラーなく実行したい。なぜならデータベースエンジンごとの方言（Dialect）の差異を吸収するためだ。
  - 受け入れ基準:
    - [Event-driven] スロットとJOINパスが解決されたとき、システムはsqlglotを用いて抽象構文木（AST）を組み立て、ユーザーが指定したSQLダイアレクト（PostgreSQL, DuckDB, SQLite, Snowflake, BigQuery等）に準拠したフォーマット済みSQL文字列を出力しなければならない。
    - [Ubiquitous] システムが生成するSQLは、常に構文的に正しく、存在しないテーブルやカラムを含んではならない。

- 要件 C-4: セマンティックメトリクス計算式の AST 展開
  - ユーザーストーリー:
    - 私はデータアナリストとして、メタデータに定義された集約メトリクス（例: `SUM(price) / COUNT(DISTINCT customer_id)`）が、自然言語の要求に応じて正確に SQL SELECT 句に展開されてほしい。なぜなら複雑な計算指標を手書きせずに再利用するためだ。
  - 受け入れ基準:
    - [Event-driven] クエリで要求されたメトリクスが Ossie で定義されているとき、システムは定義された計算式（`expression`）を AST ノードとして SELECT 句に展開し、必要なテーブルを自動的に JOIN 対象に追加しなければならない。

### 要件カテゴリD: Human-in-the-Loop (HITL) & 対話型CLI (Interaction)

- 要件 D-1: クエリ曖昧性の動的検出と介入要求
  - ユーザーストーリー:
    - 私は分析ユーザーとして、「売上」のように同じ言葉で複数の集計方法が存在する場合、勝手に間違った推測をせず確認してほしい。なぜなら誤った集計結果に基づく意思決定を防ぐためだ。
  - 受け入れ基準:
    - [Event-driven] Jevの判別結果において複数の解釈候補（同一シノニムを持つ複数メトリクスの競合や確率拮抗）が検出されたとき、システムは処理を自動中断し、メタデータの候補情報から動的に選択肢を組み立てて確認理由を提示する介入要求（HITL Issue）を発行しなければならない。

- 要件 D-2: スラッシュ構文による対話的条件補正と再実行
  - ユーザーストーリー:
    - 私はCLIユーザーとして、曖昧性の確認に対して簡単に補足条件を指定して再実行したい。なぜなら元のクエリを最初から打ち直す手間を削減するためだ。
  - 受け入れ基準:
    - [Event-driven] ユーザーがクエリ末尾にスラッシュ構文（例: `/ Aで` または `--clarify A`）を付与して実行したとき、システムは補足指定を正しく解釈し、指定された解釈に基づいて単一の決定論的SQLを生成しなければならない。

- 要件 D-3: AIエージェント向け機械可読CLI & スキーマ自己検査機能
  - ユーザーストーリー:
    - 私はAIエージェントとして、Text-to-SQLエンジンをサブプロセスツールとして呼び出したい。なぜなら自然言語から生成されたSQL、HITL状態、レイテンシをJSONで直接受け取り、自律的な判断に組み込むためだ。
  - 受け入れ基準:
    - [Optional-feature] `--json` オプションが指定されたとき、システムは人間向けの装飾を一切排除し、完全な構造化JSON（status, sql, hitl_summary, latency_ms）を出力しなければならない。
    - [Event-driven] エージェントが利用可能なスキーマや機能の問い合わせ（`schema` サブコマンド等）を行ったとき、システムは登録されているテーブルやカラム情報をJSONで返却しなければならない。

- 要件 D-4: 人間向け対話型インタラクティブモード (Interactive REPL)
  - ユーザーストーリー:
    - 私は人間アナリストとして、対話型セッションを起動してクエリ入力からHITL確認、SQL生成までをシームレスに行いたい。なぜならコマンドを都度再実行する手間を省き、思考を止めずに連続して分析を進めるためだ。
  - 受け入れ基準:
    - [Optional-feature] ユーザーがインタラクティブモード（`interactive` サブコマンド等）を起動したとき、システムは対話型REPLプロンプトを表示し、連続的な自然言語入力を受け付けなければならない。
    - [Event-driven] 入力クエリに曖昧性が検知されたとき、システムはセッションを終了せず対話的に選択肢を提示し、ユーザーの追加入力を受け取って即座に確定SQLを合成・出力しなければならない。
    - [State-driven] ユーザーが終了コマンド（`exit` または `quit`）を入力するまで、システムは対話型セッションを維持しなければならない。

### 要件カテゴリE: 非機能要件 & 品質保証 (Non-Functional)

- 要件 E-1: 超低レイテンシ処理
  - ユーザーストーリー:
    - 私はエンドユーザーとして、クエリ入力からSQLが表示されるまで待たされることなく、即座に結果を得たい。なぜなら思考のフローを中断させずに分析を継続するためだ。
  - 受け入れ基準:
    - [Ubiquitous] システムは、Jev API通信を含む全体のクエリ処理時間を通常 100ms 以内に完了しなければならない。

- 要件 E-2: 決定論的再現性の保証
  - ユーザーストーリー:
    - 私はQAエンジニアとして、同じ自然言語とスキーマ入力に対して常に100%同一のSQLが生成されることを期待したい。なぜならCI/CDでの自動回帰テストを確実に行うためだ。
  - 受け入れ基準:
    - [State-driven] 入力クエリ、メタデータ、および補足パラメータが同一であるとき、システムは常に完全に一致するASTおよびSQLを出力しなければならない。

- 要件 E-3: 将来のMCPツール化に対応したモジュール境界設計 & pipパッケージング
  - ユーザーストーリー:
    - 私はライブラリ利用者および将来のMCPサーバー開発者として、CLIだけでなくPythonコードやMCPツールハンドラーから直接コアエンジンを呼び出したい。なぜならpipで簡単にインストールし、CLI・API・MCPのどの形態でも同一のText-to-SQLロジックを再利用するためだ。
  - 受け入れ基準:
    - [Ubiquitous] システムは `pyproject.toml` に基づいて `pip install` 可能であり、CLIエントリポイント（`deterministic-text-to-sql` 等）を自動登録しなければならない。
    - [State-driven] コアエンジン（`DeterministicTextToSQLEngine`）はCLIフレームワーク（Typer/Rich）に依存しない純粋なPythonサービスクラスとして実装され、MCPツールハンドラーから直接インスタンス化および呼び出しが可能でなければならない。
